## 仕事のしかた
1. どう作るかを**具体的・段階的**に。動く形になるよう実装する（意見・設計テキストで終わらせない）。
2. **最小変更**: 依頼の範囲だけを触る。仕様を勝手に広げない。リファクタや「ついで直し」は依頼がない限りしない（直したくなったら報告に「別件候補」として書く）。
3. **既存を壊さない**: 変更前に対象を読み、影響範囲を一言添える。周辺の書き方（命名・コメント密度・流儀）に合わせる。
4. 既存ファイルの上書きは慎重に。書く前に中身を確認する。

## 着手の3分類（まず“やれるか”を見極める）
- **実装できる**：変更範囲が明確／対象が存在／完了条件が確認できる。
- **要確認**：指示が曖昧／複数案の判断が要る → 安全側の最小実装にするか、方向性を一言確認（or L2＝advisor）。
- **実装不可（→ 止めて ren に返す）**：外部アカウント・実機・秘密情報が要る／L3に当たる。＝**正しい終わり方**。

## 環境の勘所（実機で効くやつ）
- 日本語Windowsの既定コンソールは cp932。CLI出力やファイルはUTF-8で扱い明示する（`encoding="utf-8"` / `PYTHONUTF8=1` / stdout張り替え）。
- `.cmd`/`.bat`/`.ps1` は日本語混入で cp932 パースが崩れる → **スクリプト本体はASCIIのみ**。
- JSON は BOMなしUTF-8／更新後は必ず parse 確認／改行は LF（`.gitattributes` で強制済み）。
- 異常系に強く作る（半端な行・空応答・タイムアウトで落とさない）。サブプロセスは stdin を閉じる等ハングしない作法。

## 確認の作法（渡す前に）
- 検索は `rg` 優先。更新後は対象ファイルを**読み直す**。
- JSON は parse 確認／Python は `py_compile`／JS は `node --check`。
- **iPhone実機・実アカウント・外部公開が要る確認はできない** → 手順を書いて ren に渡して止める（勝手に「たぶん動く」で閉じない）。
